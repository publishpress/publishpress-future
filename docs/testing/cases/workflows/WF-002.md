# Workflow moves post to Draft immediately or after scheduled delay

## Scenario

Two parts in one case, same free workflow building blocks:

- **Part A:** Trigger **Post is published** (`onPostPublish`) → action **Move post to status** (`movePostToStatus`) = **Draft**, no **Schedule delay** (`scheduleDelay`). Publishing a matching post should move it to Draft without waiting on a clock.
- **Part B:** Same trigger → **Schedule delay** **1 day** → **Move post to status** = **Draft**. Publishing a matching post should leave it **Published** immediately and register a pending scheduled step viewable on Scheduled Actions.

Use separate workflows and posts for Part A and Part B. Do not invent Scheduled Actions column names.

## Steps

**Part A — immediate Draft**

1. As an administrator, create and publish an Action Workflow in the editor (`page=future_workflow_editor`).
2. Add trigger **Post is published** (`onPostPublish`).
3. Add **Move post to status** (`movePostToStatus`) → **Draft**. Do not add **Schedule delay**.
4. Publish a new post that matches the workflow conditions.
5. Refresh the post in the editor or list; note status (no intentional delay waiting).

**Part B — delayed Draft**

1. Create and publish a second workflow: **Post is published** → **Schedule delay** (`scheduleDelay`) **1 day** → **Move post to status** → **Draft**.
2. Publish a new matching post (not used in Part A).
3. Confirm post status right after publish.
4. Open **Scheduled Actions** (`wp-admin/admin.php?page=publishpress-future-scheduled-actions`) and find the row for that post/workflow.

## Expected result

**Part A:** The post’s status becomes **Draft** soon after publish (no multi-day wait).

**Part B:** The post remains **Published** immediately after publish. **Scheduled Actions** lists **a pending scheduled step for that post** (exact columns/labels per screen).

## Edge cases

**Part A:** Conflicting future actions or other workflows on the same post can change status; use an isolated post type or disable overlaps. Inactive workflow → post stays Published.

**Part B:** Deactivate Part A’s workflow or narrow conditions so both workflows do not fire on the same post. Advancing server time or running the queue to completion is out of scope; this part only checks immediate status plus pending scheduled step visibility.
